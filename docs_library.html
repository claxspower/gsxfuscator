01V0.6 release and verification⌄

GsXFuscator V0.6.0 — SEAL3 / VM9 hardening release

Source: User-provided GgSsXx.zip, based on the earlier SEAL2 build. The core VM9 compiler, ChaCha20/SipHash bytecode format, flow transforms, selfmod, anti-debug, anti-tamper, Graphite UI and strong policy are preserved. The default sealed packaging changes to SEAL3 over SEAL2, so old tests that assert the V0.6 wrapper syntax must be migrated.

Security scope: A standalone Lua file necessarily contains everything required to recover and execute itself. SEAL3 raises automated static extraction effort and adds runtime integrity checks; it does not prevent a determined analyst from observing the decoded program, extracting a runtime key, intercepting load, dumping process memory or patching guard logic. All bundled keys are recoverable. Obfuscation, not tamper-proof DRM or a cryptographic trust boundary.

Concepts in one page

Lexing reads text into tokens and preserves token positions. Parsing builds a syntax tree respecting operator precedence. Binding resolves locals, globals and upvalues; renaming before binding breaks shadowing. Transforms change representations while preserving observable effects. Compilation lowers normalized AST into a register-oriented instruction set. VM generation translates those abstract instructions into build-specific handler IDs and a dispatch loop. Packing serializes the prototype tree and constants; optional self-modifying storage changes when instructions are decoded. Sealing packs the VM text into a reversible outer transport. Verification attempts to show that original and protected code behave the same in a finite set of environments.

Compatibility matrix and caution

  • The source is designed for portable Lua constructs and includes Luau-specific handling, but a parser accepting a syntax form is not proof that all runtime behaviors match on all Lua versions.
  • Lua 5.1 lacks _ENV, //, bitwise operators and 5.4 integer semantics. Lua 5.4 adds different integer and GC semantics. Luau has additional syntax and host APIs.
  • The downloadable toy VM example intentionally handles only return of a numeric arithmetic expression and does not pretend to support full Lua.
  • Some historical architecture documents describe numeric goals or tests that are not current guarantees.

How to contribute to docs

When changing a serialized format, update VM-ISA-AND-BYTECODE.md or SEAL-FORMAT.md, add a golden-vector test and version the format if backward compatibility breaks.

04Build your own obfuscator⌄

Build Your Own Lua Obfuscator — A Complete Learning Path

This guide teaches a practical, testable compiler pipeline, not a trick consisting of regex substitutions or stacked encodings. You can develop your own implementation, borrow architectural ideas from GsXFuscator V0.5, and understand exactly where source compatibility can break.

0. Prerequisites and project goals

You should understand Lua tables, closures, lexical scope, functions, loops and metamethods. A minimal build environment needs a native Lua interpreter and a text editor. For a production-quality tool you will eventually need a test matrix across Lua 5.1–5.4 and, separately, your intended Luau runtime.

Define an explicit goal before creating transforms:

  • Supported source language/version and extensions.
  • Allowed output runtimes; whether load is allowed or unavailable.
  • Correctness model: same observable results, errors, side effects and global behavior.
  • Transformation goals: rename symbols, hide literals, reduce string searches, virtualize selected code.
  • Security boundary: a client-controlled interpreter can inspect its own state; the objective is analysis friction and tamper detection, not unbreakability.
  • Performance and output-size budgets; run measurements rather than guessing.

1. Lexer: recognize source without changing meaning

The lexer converts source bytes into a sequence of positioned tokens. Typical tokens: keyword (local), name (x), number (1.25), string ("hello"), punctuation ((, )), operators (.., //, ==), and EOF. Record line, column and raw lexeme when helpful.

Critical behavior

  • Distinguish -- comments, long comments --[=[...]=], and long strings [==[...]==].
  • Handle escaped quotes without terminating early.
  • Recognize longest operators first (... before .. before .).
  • Preserve numeric meaning, including hex floats and integer subtleties.
  • Report malformed strings/escapes with positions; never silently merge tokens.

Bad approach:

-- Incorrect: a textual rename can change strings, comments and globals.
source = source:gsub("user", "a")

Preferred approach: lexical name tokens feed a binding-aware AST pass. The actual GsXFuscator lexer is in v2/src/lexer.lua; use v2/examples/inspect_ast.lua to inspect what it recognizes.

2. Parser: grammar and operator precedence

A real parser tracks expressions, statements, blocks, functions, labels and table constructors. Pratt parsing is well-suited for expressions: you parse a left expression and repeatedly consume operators whose binding power permits attachment to that left side.

Important precedences to test: ^ is right-associative; .. is right-associative; multiplication binds more tightly than addition; not does not have the same precedence as a comparison; logical and and or short-circuit. Do not transform an expression as though operations were purely mathematical, because Lua metamethods can observe evaluation order.

Start with return (2+3)*4. Then add locals, function calls, closures and if/while. Every syntax addition should have at least a positive parse case, a bad-input case and a behavior-equivalence case.

Source mapping matters: an error at byte 812 should be reported as a human-readable line/column rather than an opaque crash.

3. AST contract: a stable tree between passes

A normalized AST should separate syntax (node type and children) from analysis metadata (binding IDs, scopes, upvalue flags) and preserve relevant source coordinates. Avoid hidden contracts like “every third child is the condition” unless they are documented.

Example conceptual nodes (not a literal GsXFuscator serialization):

Chunk
└── Return
    └── BinaryOp(*)
        ├── BinaryOp(+)
        │   ├── Number(2)
        │   └── Number(3)
        └── Number(4)

GsXFuscator's actual normalizer (src.ast) produces table nodes carrying type, children, line, col, with type-specific metadata. Public helpers include Ast.normalize, Ast.walk, Ast.find, Ast.count, and Ast.validate. See Compiler and AST.

Golden rule: after every AST transform, run an invariant check and compare behavior.

4. Lexical scope: the first serious correctness barrier

Renaming safely requires a symbol table, a scope stack, lexical declaration rules and captured-variable tracking.

Consider:

local x = 10
local function outer()
  local x = 20
  return function() return x end
end
return x, outer()()

A correct rename preserves 10, 20 and the inner function's capture. You must also handle:

  • local x = x (RHS resolves in the outer scope).
  • local function f() (self-reference is visible inside the body).
  • Function parameters shadowing outer names.
  • Closures capturing loop variables and mutable upvalues.
  • repeat ... until condition seeing body locals.
  • goto and labels not crossing function boundaries.
  • Explicit globals and _ENV in Lua 5.2+ versus 5.1 environments.

Use a unique bindingId or equivalent for every declaration; rename references by binding identity, not by spelling. Never blindly rename _G or host API names.

5. Source transformations: keep semantics before disguising syntax

Start with local renaming. Add constant rewriting only when you can prove it preserves number type, overflow behavior, precision, metamethod selection and expression order. For strings, a pool/decoder may complicate static scanning, but its key and code ship with the output and are reversible.

For control-flow flattening, transform a statement block into a state machine. Record how break, continue, return, labels, exceptions, multiple assignment and closure capture map to states. Do not flatten across arbitrary function boundaries, reorder side-effecting calls or change the number of evaluations.

Unit-test transformed code under equivalent environments. An AST that is syntactically valid can still be semantically wrong.

6. Bytecode compiler: explicit intermediate representation

Define an instruction format before VM code generation. A simple educational stack machine has:

Instruction Stack effect Behavior
PUSH n +1 Push constant n
NEG 0 Negate top
ADD/SUB/MUL/DIV -1 Pop two, push result
HALT no change Return stack top

GsXFuscator itself uses a register VM and a larger ISA; see VM and ISA. A starter project should deliberately implement fewer instructions and validate them completely.

Instruction invariants: known opcode; expected operand types; in-bounds register/stack use; well-formed jump target; legal terminal state. Disallow missing fields and nonsensical values before dispatch.

7. The runnable miniature: learn the whole pipeline

File: v2/examples/toy_vm_obfuscator.lua. This code is independent of the GsXFuscator compiler and intentionally easy to study.

Create an input file:

return -(11 - 3) * 2

Compile it:

lua v2/examples/toy_vm_obfuscator.lua expr.lua expr.obf.lua 12345
lua v2/examples/toy_vm_obfuscator.lua expr.lua expr.alt.lua 67890

The program:

  1. Tokenizes a deliberately small Lua expression subset.
  2. Parses return, parentheses, decimal literals, unary minus, +, -, *, /.
  3. Emits postfix stack instructions.
  4. Assigns numeric opcode IDs from a deterministic seed.
  5. Emits a self-contained Lua VM and executable instruction table.
  6. Rejects everything outside its documented grammar.

Test with python v2/examples/test_toy_vm.py. The six positive and four negative cases are part of the teaching materials, not full language conformance. The output returns -16 for the input above.

Exercises in order

  1. Add source-position reporting for parser errors; track the real cursor on every token.
  2. Implement exponentiation (^) with right associativity and test 2^3^2.
  3. Add variable declarations and a lexical environment before supporting Name expressions.
  4. Add JMP and JMPF with a target validation pass.
  5. Add calls and multiple return values; preserve evaluation order and Lua's nil-return semantics.
  6. Support closures: bind upvalues to cells shared between closures.
  7. Add tables, metatables, and metamethod-sensitive operations.
  8. Introduce function prototypes and a constant pool.
  9. Add a packer with explicit version, length and checksum; distinguish corruption detection from authentication.
  10. Run cross-version compatibility tests; only then add alias opcodes or control-flow flattening.

8. Randomized opcode mapping, correctly explained

Opcode polymorphism assigns different numeric IDs to the same logical instruction in different builds. The emitted dispatch must use the same mapping as the compiler. Fix the seed to make failures reproducible; vary it to test build diversity. Never call this key secrecy when the interpreter contains the mapping.

In the mini example, keys are permuted and embedded in both instructions and dispatch branches. The VM can therefore run in any supported Lua process without asking for a secret. This is obfuscation, not encryption.

For production, consider a per-prototype mapping and operand layouts only after your base compiler passes differential tests.

9. Packing and delivery modes

Separating compilation and packaging simplifies testing:

source → AST → compiled prototypes → VM source
                                      ├─ direct VM artifact
                                      └─ sealed transport → loader → VM

The sealed wrapper in this project uses reversible Base64-like encoding, rolling XOR/PRNG and optional LZSS; the client must decode it. Runtime loading through load is observable. A direct VM avoids that extra loading point, but reveals the VM source at rest. Neither choice gives a cryptographic trust boundary.

In a fresh implementation, do not add a wrapper until the direct form is correct and independently testable.

10. A realistic test strategy from day one

Correctness

  • Tokenizer golden vectors and invalid escapes.
  • AST shape snapshots and parser precedence tests.
  • Scope/rename tests with shadowing and upvalues.
  • Metamethod-sensitive arithmetic, table access and equality.
  • String bytes, nulls, Unicode source, long brackets.
  • Function varargs, tail calls, multiple return values, error messages.
  • Versions: Lua 5.1, 5.2, 5.3, 5.4 and the particular Luau target.

Security assumptions

  • Manipulate operand, opcode, prototype length and block checksum separately.
  • Verify that protections fail closed on malformed data.
  • Test that no unmodified supported program spuriously fails an anti-debug probe.
  • State explicitly that the code and decoding secrets in distributed artifacts can be inspected.

Performance

Benchmark a source program and a protected program with identical inputs, recording compilation time, cold start, steady-state work, output bytes and peak memory (where available). Use medians plus dispersion; don't call one unusually fast run a general speedup.

See Testing and Benchmarking for a full acceptance matrix.

11. Turning the learning project into a maintainable tool

Before shipping to users:

  • Separate parser, semantic analysis, compiler, VM and packer modules.
  • Keep protocol schemas and format versions explicit.
  • Add deterministic seeds, input-size limits and stable, human-readable errors.
  • Avoid silent fallbacks that remove protection without telling the user.
  • Make build artifacts reproducible with an explicit seed.
  • Build automated regression tests for each layer and a cross-runtime matrix.
  • Write license, support and threat-model documentation.
  • Publish measured performance and label experimental protections as experimental.

05Lexer, parser, AST & scope⌄

Compiler Front End, AST, Scope and Semantics

Source of truth: v2/src/lexer.lua, parser.lua, ast.lua, scope.lua, compiler.lua. This describes the current V0.5 implementation, not a guaranteed stable plugin ABI.

1. What each component owns

File Responsibility Input → output
lexer.lua Lexical scanning and diagnostics UTF-8 source bytes → token list, errors
parser.lua Grammar (recursive descent / Pratt expressions) source → parser AST + errors
ast.lua Normalize, walk, count, validate parser tree → consistent type/children tree

The main orchestrator calls these in src/obfuscate.lua, with additional passes in between. Do not call Compiler.compile before the AST has been normalized and scope-analyzed unless you understand the constraints of that particular test.

2. Lexer contract

local Lexer = require('src.lexer')
local tokens, errors = Lexer.lex('local x = "hello"', 'sample.lua')
assert(#errors == 0)
for i, token in ipairs(tokens) do
  print(i, token.t, token.v, token.line, token.col)
end

Tokens carry t and source coordinates line, col; some types also carry v and raw. The lexer recognizes Lua keywords, numeric literals, quoted/long strings and long comments, operators, and selected Luau syntax extensions. Lexer.KEYWORDS is exposed, but simply adding a word to it does not implement parsing or code generation for that word.

Escapes and edge cases

  • Single- and double-quoted strings, escaped quotes and backslashes.
  • Numeric escapes, \xNN, \u{...}, line continuations, and \z whitespace skipping.
  • [=[...]=] long strings and --[==[...]==] long comments.
  • Multi-character operators (longest match).
  • Unicode bytes in string contents and position diagnostics.
  • Error locations for unfinished strings or illegal token sequences.

Test rule: for each feature, add a valid example and an invalid example. Do not let a lexer silently consume an unexpected character as trivia.

3. Parser contract

local Parser = require('src.parser')
local rawTree, errors = Parser.parse('local x = 3\nreturn x + 1', 'demo.lua')
assert(rawTree and #errors == 0)

The parser creates a tree using its own node tags (t) and records errors rather than normally throwing syntax failures at the caller. Expressions use Parser.BINPRI precedence mappings; unary parsing, statements and scopes use recursive descent. Parse errors contain line, col, msg, and may include filename.

Syntax coverage and uncertainty

The code includes Lua 5.1–5.4 and Luau-oriented parsing. That should not be interpreted as a claim that all host-specific constructs have verified runtime behavior. A build for Lua 5.1 must not casually inject syntax that exists only in 5.4; emitted VM code uses a portable subset for this reason.

4. Normalized AST contract

local Ast = require('src.ast')
local tree = Ast.normalize(rawTree)
local violations = Ast.validate(tree)
assert(#violations == 0)
local metrics = Ast.count(tree)
print(metrics.nodes, metrics.maxDepth, metrics.leaves)
Ast.walk(tree, function(node, depth, parent)
  print(depth, node.type, node.line, node.col)
end)

Normalized nodes contain at least type, children, line, col; additional fields depend on the node type. Ast.find(tree, 'BinaryOp') returns matching nodes. Ast.count returns nodes, maxDepth, leaves, and byType counts. The AST is not a plain text rewriter: many transformations consume child positions and metadata. Read ast.lua before mutating nodes.

Representative node types

Category Typical nodes Watch for
Root Chunk top-level return, varargs
Variables Name, Local, Assign local/global identity and shadowing
Expressions Number, String, BinaryOp, UnaryOp, Call evaluation order, metamethods
Functions Function, LocalFunction, Return closures, varargs and multiple results

Other labels, goto, Luau-oriented variants runtime-specific compatibility

5. Scope and binding contract

local Scope = require('src.scope')
local plan = Scope.analyze(tree, {seed=123, prefix='_0x'})
assert(#plan.errors == 0)
Scope.apply(plan)

Scope.analyze annotates names with binding IDs / reference kinds before Scope.apply mutates declarations and references. It reserves existing names to avoid collisions. Globals remain global; _G and _ENV are handled deliberately. A renamed local must keep exactly the same links to its references and upvalues.

Correctness examples

local x = 1
local function f()
  local x = 2
  return function() return x end
end
return x, f()()  -- expect 1, 2

local y = 5
local function g()
  local y = y     -- the initializer refers to the outer y
  return y
end
return g()       -- expect 5

local count = 0
local function inc()
  count = count + 1
  return count
end
return inc(), inc()  -- expect 1, 2; same captured storage

When a name is rebound or captured, copying its string spelling is not enough. Binding identity is the invariant.

6. Compiler and prototype format

local Compiler = require('src.compiler')
local compiled = Compiler.compile(tree, {})
assert(#compiled.errors == 0)
local problems = Compiler.validate(compiled)
assert(#problems == 0)
for i, p in ipairs(compiled.protos) do
  print('proto', i, '#code', #p.code, '#const', #p.k)
end

Compiler.compile returns {protos = {...}, errors = {...}, stats = {...}}. A proto contains at least:

{
  code = { {op='LOADK',a=1,b=0,c=0,d=1}, ... },
  k = { ... },      -- constant pool
  params = 0,
  vararg = true,
  maxstack = 1,
  updesc = { ... }, -- closure upvalue descriptors
}

Instruction fields are op, a, b, c, and d. Registers are 1-based; register 0 is not a normal allocated register. The full instruction list is Compiler.OPS and the count is Compiler.OPCOUNT. Compiler.validate checks compiler output before VM randomization.

Registers vs stack machine

The teaching example is stack-based because it is easier to learn. The real VM is register-based: LOADK A D loads K[D] into R[A]; MOVE A B copies a register; CALL A B C D needs careful handling of varargs and multiple return values. This is why a realistic Lua compiler is more complex than the toy.

Details people regularly get wrong

  1. Multiple assignment: Lua computes the RHS expressions before assigning LHS targets; don't rewrite sequentially.
  2. Multi-return adjustment: last call/vararg in a list expands in some contexts but collapses elsewhere.
  3. Short-circuit logic: and/or return operands, not arbitrary booleans.
  4. Metamethods: arithmetic, equality, length, indexing, calls and concatenation can run user code.
  5. Numeric differences: //, bitwise ops, 64-bit integers, float coercion and overflow vary by runtime.
  6. Tail calls: can affect stack traces and recursion limits.
  7. Upvalues: a closure must capture the same cell, not a stale value snapshot.
  8. Error semantics: changing evaluation order changes which error surfaces first.
  9. _ENV and getfenv: different language versions use different environment rules.
  10. Iteration: don't change hash/table iteration behavior without a clear contract.

7. Extension design: a safe new AST pass

A new transformation should accept and return the normalized AST, have deterministic seed handling, and preserve invariants. A minimal no-op pass looks like:

local Ast = require('src.ast')
local MyPass = {}
function MyPass.run(tree, opts)
  assert(Ast.isNode(tree), 'normalized AST required')
  opts = opts or {}
  -- Inspect nodes, then apply only proven semantic-preserving changes.
  Ast.walk(tree, function(node)
    if node.type == 'Number' then
      -- Intentionally no mutation: changing raw numeric representation
      -- without checking integer/float semantics can break programs.
    end
  end)
  assert(#Ast.validate(tree) == 0)
  return tree
end
return MyPass

Integrate it into src/obfuscate.lua only after it has a dedicated unit test and an end-to-end behavior test. The sequence of existing passes matters because a later pass may depend on fields created by an earlier pass.

06VM ISA, bytecode & selfmod⌄

VM, Register ISA, Bytecode Container and Runtime Execution

V0.5 source files: src/compiler.lua, src/vmgen.lua, src/bytecode.lua, src/selfmod.lua, src/integrity.lua, src/antidebug.lua. Audience: implementers building their own VM or extending this compiler's internals.

This file documents the source design. The VM and bytecode internals are not a stable public ABI. In particular, opcode IDs and masks may differ by build seed, and the format should be treated as opaque unless the same version's pack/unpack logic is used.

1. Execution path

Normalized, bound AST
   ↓ Compiler.compile
Prototype tree: code, constants, parameters, upvalues
   ↓ VMGen.randomize
Build-specific opcodes, layouts, masks, handler plan
   ↓ optional Selfmod.apply
Encrypted instruction blocks / lazy decode metadata
   ↓ Bytecode.pack
Packed prototype stream → encrypted payload → header/trailer
   ↓ VMGen.emit
Lua source with VM decoder, runtime, handler table, checks
   ↓ optional Seal.wrap
Reversible outside transport (loader); runtime load() of VM text

Direct VM emits the VM runtime source without wrapping it in the outside loader. The runtime may still decode internal bytecode, but it does not need the seal-stage load of a second VM script.

2. Instruction schema

Compiler.compile emits {op="NAME", a=number, b=number, c=number, d=number}. The exact use of operands depends on op. Abstract opcodes are semantic operations; emitted numeric keys are build-specific.

Value/register movement

Opcode(s) Behavior (simplified)
MOVE A B R[A] = R[B]
LOADK A D Load K[D] into R[A]
LOADINT A D Load an immediate integer into R[A]
LOADBOOL A B Load a boolean
LOADNIL A, LOADNILN A D Clear one / a range of registers
GETUPVAL, SETUPVAL Access captured upvalue cells
NEWCELL, GETCELL, SETCELL Support mutable captured locals
SETTOP A Update runtime top marker

Globals and tables

Opcode(s) Behavior (simplified)
GETGLOBAL, SETGLOBAL Host-global reads and writes
NEWTABLE Allocate Lua table
GETTABLE, SETTABLE Indexed read/write
GETFIELD, SETFIELD Constant-key table access
GETIDXI, SETIDXI Immediate numeric-key table access
SELF Prepare method call plus receiver
SETLIST Populate array-style table fields

Arithmetic, string, comparison and tests

ADD, SUB, MUL, DIV, MOD, POW, IDIV, UNM, CONCAT, LEN, NOT, BOOL; bitwise arithmetic BAND, BOR, BXOR, BNOT, SHL, SHR; comparisons EQ, NE, LT, LE, GT, GE; immediate/constant variants such as ADDK, ADDI, EQK, LTK (see Compiler.OPS for the full inventory).

Control and function operations

Opcode Behavior (simplified)
TEST, TESTSET, TESTNIL Conditional evaluation/skip
JMP, JMPF, JMPT Relative jump; target validation matters
FORPREP, FORLOOP Numeric loop setup/advance
TFORCALL, TFORLOOP Generic iterator loop
CALL, TAILCALL, RETURN Call, tail call, return/multiple return handling
CLOSURE Create closure from child prototype
VARARG Read variable argument count
CLOSE Closing/upvalue-related barrier
NOP No-op

Do not assume all opcodes have the same register usage. Some use constants or an immediate in d, some use b/c as counts, and some have relative jump offsets. The authoritative instruction comments are at the start of src/compiler.lua.

3. Prototypes and closures

A compiled prototype contains code (P.code), constants (P.k), parameters (P.params), vararg flag (P.vararg), maximum register allocation (P.maxstack) and upvalue descriptors (P.updesc). Nested functions become separate prototypes; closure creation refers to those prototypes. Captured locals must share mutable cells with every closure that closes over them.

Conceptual execution frame:

R : register array (1-based)
K : constants belonging to the prototype
U : captured upvalue cells
pc: program counter
S : frame bookkeeping (top, arguments, returns, etc.)

A VM that copies upvalue values instead of sharing cells will silently change program semantics. Test closure mutation and loop captures first.

4. Opcode mappings and polymorphic handlers

VMGen.randomize(compiled, {seed=..., decoys=..., encodings=...}) validates compiled prototypes then creates a plan. In the current source it assigns a shuffled dense slot pool and computes numeric keys from a per-build keyBase plus a slot. Each abstract instruction may have multiple aliases; selected operand positions and masks vary across aliases. Decoy handlers occupy additional keys.

The dispatcher uses a function table, not a single static readable elseif ladder for every canonical opcode. The emitted VM contains a consistent mapping between bytecode keys, masks and handler bodies. This is not a hidden-key scheme: the runtime necessarily has the data needed to execute.

How to extend safely

Adding an abstract opcode requires coordinated changes:

  1. Update Compiler.OPS and compiler lowering.
  2. Define the VM handler semantics in vmgen.lua.
  3. Update operand encoding/decoding if the instruction needs a new operand class.
  4. Update compiler validation and runtime instruction-shape checks.
  5. Add positive, negative and metamethod-sensitive tests.
  6. Verify direct and sealed outputs and all supported Lua runtimes.

Changing numeric IDs alone is easier, but is not equivalent to changing semantic opcode definitions.

5. Packed bytecode format (V0.5 format version 9)

Bytecode.pack(plan, opts) returns a package table containing blob, key, version, plainLength, plainBytes, cipherBytes, blobBytes, checksum and keyTag. Internal Bytecode.VERSION is 9.

Container layout

Byte offset Size Content
0–3 4 FNV-1a32 checksum of ciphertext body (little endian)
4–7 4 Plaintext body length (little endian)
8–11 4 Build-key-derived tag (little endian)
12–15 4 Per-build format marker bytes derived from tag
16 … n-9 variable ChaCha20-processed ciphertext body
last 8 8 SipHash-2-4 trailer covering header + ciphertext (little endian words)

The exact parser is Bytecode.parseHeader; it refuses blobs shorter than 24 bytes and returns structured fields: checksum, plainLength, keyTag, version, magic, body, tag.

Security interpretation: the keyed trailer derives from values reconstructed within distributed code, ultimately a 32-bit build seed; do not present it as independent, secret-key, cryptographic authentication. It does make accidental or naive corruption detection more involved than a lone checksum.

Plaintext body

The packer serializes a prototype count and per-prototype fields: parameter/vararg information, instruction count, numeric opcode/operands, constants and upvalue descriptors. Integers use a variable-length format; signed values use zigzag encoding where applicable. Constants are tagged/length-prefixed. Reading requires strict bounds and exact type handling.

Encryption/mixing

bytecode.lua implements a ChaCha20-compatible 20-round core with portable arithmetic and optionally faster build-host operations. That arithmetic is careful about 32-bit overflow and 5.1 compatibility. The emitted VM decoder mirrors the format; it contains enough information to reconstruct the bytecode. ChaCha20 primitives do not make an embedded client-side build seed secret.

Parsing and validation

A safe decoder must:

  • Require correct minimum container size and internal version.
  • Check authenticated/checksummed ranges with the exact intended byte order.
  • Reject malformed or overlong variable integers and forbidden values.
  • Enforce prototype counts and total byte/operation budgets.
  • Prevent cursor overruns in every nested section.
  • Check operand types, bounds and jumps before execution.
  • Fail closed on unknown opcode IDs and corrupted padding.

The project has regression tests for several of these classes; neither the presence of code nor a green unit test proves that every attack is prevented.

6. Lazy block decoding and self-modifying storage

In the strong profile Selfmod.apply(plan, {seed=...}) can rewrite prototype code into block metadata. It records the total instruction count (P.total), encrypted blocks (P.blocks), block chain state, block size and cache cap, and empties P.c as part of representation change. The emitted runtime can decode instructions on demand and may evict/re-encrypt cached blocks.

Two lengths must not be confused:

  • Total logical instruction count of the prototype.
  • Number of currently decoded instructions in a cache/window.

A preflight that only checks #decoded_cache against the total count will fail for legitimate lazy implementations; a preflight that stores 0 for every expected length fails to check anything. The V0.5 prototype length checks intentionally distinguish total metadata and current cache residency.

Selfmod.replay is a test helper that exercises the decode/evict/re-encrypt lifecycle on copies of the blocks. It is not a public high-level build API.

7. Runtime CFI and integrity checks

Checks in the emitted runtime include validation of handler identities, table/prototype shape, checksummed encoded blocks, bounds/operand forms and some runtime behavior probes. A protected metatable's __newindex does not make existing table slots immutable; independent reference checks detect certain mutations instead. Some hosts provide table.freeze, but standard Lua does not guarantee it.

The VM must validate the next program counter and instruction fields before dispatch. Short programs still need a pre-dispatch check rather than depending solely on periodic checks. See Runtime integrity and threat model.

8. Seal is a different format

Do not conflate internal bytecode with the optional external seal transport:

Property Internal VM bytecode External sealed wrapper
What it packages prototypes + instructions + constants generated VM Lua source text
Source bytecode.lua seal.lua
Layout 16-byte header + ciphertext + 8-byte tag 12-byte per-block metadata, LZSS/raw, XOR, 64-symbol alphabet
Runtime VM interpreter decode and call load/loadstring on VM text
Cryptographic secrecy no independent trust boundary no independent trust boundary

See SEAL-FORMAT.md for block details and decoder limits.

9. Test your own VM rather than trust code size

Suggested development gates:

  • A small instruction trace with expected register values after every opcode.
  • Out-of-range, fractional and zero program-counter mutation cases.
  • Invalid register index, malformed constants and missing operands.
  • Inconsistent prototype length or cache size.
  • Duplicate/unknown opcode IDs and dispatcher table mutation.
  • Nested closures with captured mutable variables.
  • Metamethod-sensitive ops and pcall/xpcall error behavior.
  • Differential comparison of original and VM programs under the same target runtime.

Key insight: more handlers, a longer loader or deeper nesting are complexity metrics, not proof of resistance to devirtualization.

Source Transformations, Pass Ordering and Extending GsXFuscator

V0.5 implementation: src/obfuscate.lua orchestrates parsing, name resolution, constant/flow/string passes, register compilation, VM randomization, self-modifying blocks, packed bytecode, and runtime emission. This is a source-architecture guide, not an externally versioned transform plugin API.

1. The exact pass order in the orchestrator

Parser.parse
  → Ast.normalize
  → Scope.analyze / Scope.apply
  → Consts.run

3. Scoped renaming: a reliable first transform

A binding-aware rename changes the spelling of locals but not their referents. It must protect globals, built-ins, user-defined globals, labels, private function parameters and captured upvalues. A global function lookup, including _G and _ENV behavior, must remain directed at the user's environment.

A minimal reference workflow:

local Parser, Ast, Scope = require('src.parser'), require('src.ast'), require('src.scope')
local parsed, errors = Parser.parse('local a = 7; return a')
assert(parsed and #errors == 0)
local tree = Ast.normalize(parsed)
local plan = Scope.analyze(tree, { seed = 123, prefix = '_0x' })
assert(#plan.errors == 0)
Scope.apply(plan)
assert(#Ast.validate(tree) == 0)

Scope.analyze and Scope.apply are internal stages. This recipe is useful for understanding the pipeline; for end-to-end output use Artifact.build() instead of inventing a new source printer.

4. Constant and string rewriting

Consts.run obscures selected scalar constants through equivalent expressions. Strings.run transforms string occurrences using an encoded pool and emitted decoder. The implementation includes multiple scheme labels such as XOR, shuffled alphabet, Huffman-oriented or other encodings in strings.lua.

Correctness hazards

  • Integer vs floating subtype (1 versus 1.0 on Lua 5.3+).
  • NaN, infinities, negative zero and unsupported numeric representations.
  • Binary strings containing \0 and bytes above 127.
  • String identity/equality after decoding.
  • Source encoding and escape semantics; UTF-8 text is not always a byte-preserving copy of a Lua string literal.
  • Decoding a string during a metamethod-sensitive evaluation can change error timing.

Test advice: run byte-level comparisons, not only printable-string comparisons. Treat the pool key as accessible to an attacker when shipped in the output.

5. Control-flow flattening

Flatten.run(ast, opts) rewrites selected source control flow into alternative AST forms, including state-machine-like shapes. This can increase static analysis work but raises correctness risk.

Transform only when you can preserve

  1. Relative ordering of side effects.
  2. Correct truthiness (false and nil are false, everything else is true).
  3. Multiple return values and the placement of tail calls.
  4. Short-circuiting and conditional evaluation.
  5. Label visibility and the scope of goto.
  6. Loop-scoped captures and repeat/until variable lifetime.
  7. break/continue semantics and error propagation.
  8. Metamethod calls and their order.

Example conceptual state conversion:

-- Original
if flag then workA() else workB() end
finish()

-- Illustration only; not an AST serialization and not a safe
-- generic textual rewrite of arbitrary Lua:
local state = flag and 1 or 2
while state ~= 0 do
  if state == 1 then workA(); state = 3
  elseif state == 2 then workB(); state = 3
  elseif state == 3 then finish(); state = 0
  else error('invalid state') end
end

This example is intentionally simple. Real Lua if may contain returns, nested scopes and calls with observable errors; a safe compiler must operate on AST/CFG, not text.

6. Opaque predicates

An opaque predicate is a condition whose outcome is known to the compiler but intended to be less obvious to a reader. Opaque.run adds selected constructs from predefined templates. A generator must test its mathematical claims for the actual numeric domain and host semantics; integer overflow and float precision can invalidate apparently tautological expressions.

Never let an opaque predicate evaluate a user expression twice. A metamethod or function call may have side effects.

7. Bytecode and runtime modifications

Compiler.compile creates semantic instructions; VMGen.randomize assigns handler keys; Selfmod.apply optionally rewrites instruction storage; Bytecode.pack serializes/encrypts a payload; VMGen.emit writes the VM. These are coupled internals.

Coordinated change checklist

For an added opcode:

  • add a compiler lowering rule and opcode name;
  • add runtime handler semantics and any variant templates;
  • add compiler validation and runtime operand checks;
  • update wire encoding for any new operand type;
  • test direct and sealed emission, selfmod and non-selfmod paths;
  • run regression tests on every supported Lua interpreter.

For a changed serialized field, update packer + loader + test vectors together and document the compatibility break. Failing to do so can yield runnable output with subtly wrong values.

8. Integration extension points

There are three practical levels:

Level A — supported integration: call Artifact.build(source, opts) and inspect result. Recommended for independent tools, editors and GUIs.

Level B — experimental compiler fork: call or modify src.obfuscate and transform modules. Keep a source fork and a test matrix because internal data layouts can change.

Level C — VM/runtime format fork: modify compiler, vmgen, bytecode, selfmod, integrity in tandem. Treat generated artifacts as a new format and create a versioned wire specification.

9. Do not mistake more complexity for more security

Added decoy handlers, bytecode encoding layers, or lengthy opaque predicates can make programs larger without defeating a capable dynamic observer. Use independent measurements:

Claim Testable question
Hides source text Does static output reveal plaintext literals and source structure?
Prevents tampering Which exact alterations are detected, and before which side effect?
Increases analyst cost How much work/time does a controlled reconstruction require?
Compatible Does the output match original behavior in each target runtime?
Fast enough What is cold-start/steady-state/peak-memory overhead?

10. Suggested learning extensions

  1. Add a metadata-only AST analysis pass (count conditional nodes).
  2. Add a deterministic local-renaming strategy and test collisions.
  3. Create a benign source-transformation pass under strict AST invariants.
  4. Implement one extra logical opcode in an isolated teaching VM.
  5. Add invalid operand and broken jump-target tests.
  6. Make a versioned serializer and round-trip parser.
  7. Benchmark before and after, recording measured size and runtime.
  8. Document the threat model and compatibility risks.

9) Compatibility and guarantees

What the public API does guarantee for V0.5:

  • programmatic build entry points exist and are documented here
  • sealed and direct delivery are both available
  • the build seed can be fixed for repeatable output
  • the build service accepts JSON requests with the documented fields

What it does not guarantee:

  • that internal modules or VM internals remain stable
  • cryptographic secrecy of distributed keys/transport
  • resistance to a hostile host with full runtime control
  • cross-version binary compatibility of generated artifacts
  • exact preservation of undocumented fields in stats/result tables

Doğrudan mod neden önemli?

Seal'i kullanırken dış decoder çalışır ve VM kodunu load/loadstring ile tekrar derler. Host bu fonksiyonları değiştirdiyse, veriyi görebilir. Direct VM bu ekstra aşamayı kaldırır; ancak birincil VM'nin Lua metnini görünür hale getirir.

Kodun kendi içinde dinamik yükleme bulunuyorsa bu ayrı bir konudur; direct VM, kullanıcı kodunun kullanımını otomatik kaldırmaz.

Seal API

Seal.wrap(text, seed, opts) metni bir Lua dosyasına dönüştürür. opts.blockSize pozitif tamsayı ve 8388608'den küçük olmalıdır; varsayılan blok 65536 ham bayttır. opts.maxBytes en büyük ham yük boyutunu belirler; varsayılan Seal.MAX_BYTES = 33554432. Limitin aşılması durumunda nil, error_message döner. Art arda aynı metin, seed ve seçenekler ile aynı çıktının üretilmesi hedeflenir.

Seal.isWrapped(text) yalnız dış banner ve beklenen taşıyıcı sentineli için sezgisel bir testtir; güvenli doğrulama işlevi değildir.

Seed çeşitliliği ve deterministik build

src/entropy.lua, /dev/urandom varsa 4 bayt alır. Host bu kaynağı sunmuyorsa süreç saati, math.random ve iç sayaçla best-effort fallback kullanır. Fallback kriptografik olarak güvenli değildir. Kısmi çıktıyı önleme

CLI önce hedefin yanında geçici dosya yazar, ardından close() başarılıysa os.rename() uygular. Hedef zaten varken rename'e izin vermeyen Windows dosya sistemlerinde, eski dosya silinmek yerine hata döner. Bu, her sistemde tam atomiklik/durability garantisi değildir.

4. Request schema

POST /api/build expects JSON, Content-Type: application/json:

{
  "source": "print('hello')",
  "preset": "strong",
  "seed": 12345,
  "rules": {
    "flatten": true,
    "opaque": true,
    "selfmod": true,
    "antidebug": true,
    "integrity": true
  }
}

Top-level request fields are only source, preset, seed, rules. Other keys are rejected by Python validation. rules is an object whose allowed keys are those five names and whose values must be booleans; this is a private service contract, not the browser's unlocked public settings. The local server validates syntax/types; the CLI has additional flags not accepted by the HTTP API.

Limits in current implementation

Constraint Value Enforced by

Source field UTF-8 length 10 MiB web/service.py
Build subprocess wall timeout Not imposed by application web/service.py
Build return artifact 32 MiB web/compile_job.py
Concurrent build slots 2 web/service.py
Total connections 24 web/service.py

Some limits are implementation constants, not contractual service-level guarantees. Different hosting layers can impose smaller limits or stricter timeouts.

12Security and threat model⌄

Runtime Integrity, Anti-Debug and the Actual Security Boundary

This is a security engineering reference for GsXFuscator V0.5. It describes defensive detection, its observable limits, and how to test without inventing guarantees.

1. Assets and attacker capabilities

Assets may include source structure, bytecode layout, runtime state, and resistance to simple patching. Attackers may have varying control:

Level Typical capabilities What defensive controls can reasonably do
Source file observer Inspect, edit, grep, diff distributed Lua Obfuscate syntax, obscure names, detect some edits
Script runtime observer Install hooks, inspect globals, step through Lua Detect some changes and runtime anomalies
Full host controller Replace interpreter, patch/debug memory, alter calls No reliable absolute protection from inside the same Lua process

A complete threat model also asks what the protected code is allowed to do. Obfuscation never substitutes for server-side authorization, key custody or safe sandboxing.

2. Distinguish the layers

Layer Mechanism What it detects/resists What it does not prove
Seal Per-block FNV + Adler, lengths and boundaries Accidental or naive payload modification Secret-key authentication
Bytecode container Checksums, derived SipHash trailer, bounds Many malformed/corrupt blobs Secrecy against full runtime control
VM handler references Independent pinning and runtime cross-checks Selected handler replacement/mutation Immutability of Lua tables
Prototypes Total-length and current-window validation Some metadata/cache alteration All possible decoder attacks
Control-flow checks pc, operand, branch shape validation Invalid state/jump tampering Prevention of semantic devirtualization
Anti-debug probes debug.gethook/behavioral checks in supported contexts Selected hooks/altered standard functions Detecting every debugger

CRC, FNV and Adler are not MACs

FNV-1a and Adler-32 are checksums. A capable editor can change both the protected data and a checksum constant. An unforgeable authorization decision requires a trust boundary outside the attacker's control. Even a keyed MAC loses that property if its key and trusted verification logic are fully available to the same attacker in the client process.

Metatables are not immutable storage

__newindex is not invoked for an ordinary assignment to an existing table field. rawset bypasses it. A protected __metatable field hides the metatable from ordinary getmetatable but does not make the original table immutable. Reference comparisons help detect changes; they are not the same as preventing changes. Some Luau environments offer table.freeze, but standard Lua does not.

3. Runtime checkpoints

For meaningful fail-closed behavior, a protection should check the relevant state before using it. A check only every 1,000 dispatches may never execute in a two-instruction program. Conversely, checking every handler at every step can impose substantial overhead.

Recommended checkpoints:

  • Startup: shape and expected metadata/handler references before first dispatch.
  • Dispatch: validate current instruction and program counter.
  • Branch: validate next target and conditional operand shape.
  • Periodic: audit a rotating portion of the handler/prototype inventory.
  • Decode: verify block length, bounds and checksum before admitting decoded instructions.
  • Termination: leave the runtime in a consistent state; no fallback to unchecked behavior after failure.

The current emitted VM contains a combination of such checks. The actual strength depends on whether the tested attack reaches a guarded path; use mutation tests, not code counts.

4. Anti-debug philosophy

A runtime check is a signal: active hook or unexpected standard function behavior may be caused by debugging, profiling, instrumentation, or a legitimate host integration. The objective is to report/stop under a known policy while minimizing false positives.

Do

  • Capture expected references before untrusted code can replace them when practical.
  • Query only supported debug APIs, inside guarded calls when they can be missing.
  • Avoid mutating the host's hook state merely to test it.
  • Make failure behavior predictable and testable.
  • Test with and without the debug library and with benign profiling hooks.
  • Document potential false alarms in embedded/Roblox/luau-like hosts.

Avoid

  • Claiming that debug.gethook sees every instrumentation technique.
  • Setting a hook and failing to restore pre-existing host hooks.
  • Infinite loops, destructive behavior or arbitrary external calls as a reaction to a suspected debugger.
  • Relying on secret static tables distributed alongside the protected script.

5. How to write controlled live tests

Build a known fixture under a fixed seed. In a separate, authorized test runtime, introduce one mutation and assert whether the expected integrity error occurs.

Example classes:

Mutation Expected defensive outcome
Replace one live handler function Detect before or at handler execution
Replace both live and backup references Independent anchor/check catches tested mutation
Add unexpected table entries via rawset Shape/count check catches tested mutation
Remove or alter a prototype's expected length Prototype metadata check catches tested mutation
Use a zero or fractional program counter Runtime rejects invalid PC
Redirect a jump to an out-of-bounds target Branch target validation rejects
Corrupt a sealed chunk checksum or length Seal decoder aborts
Install a Lua hook during execution Selected hook probes report/stop when reachable
Run without a debug library Legitimate supported clean execution should continue

Record both detection and missed cases. Test with a clean control and repeat across seeds. A test that injects a corrupt field before the decoder gets there is not equivalent to arbitrary live code mutation in a hostile interpreter.

6. What runtime dumping can reveal

The external sealed wrapper reconstructs an obfuscated VM Lua script and passes it through load/loadstring. Tracing that call can reveal the inner VM script. That is not necessarily the original input source. A direct VM artifact omits the outer dynamic load stage but exposes the VM script statically. With access to interpreter memory and hooks, an analyst may still inspect execution state.

Devirtualization would additionally reconstruct program semantics from virtual instructions, constant pools and handler behavior. A static source-recovery tool failing once is not proof the VM is undevirtualizable.

7. Build-time and runtime secrets

  • Treat build seed and emitted key material as recoverable, not secret.
  • Do not ship cloud credentials, license authority or critical authorization decisions to the Lua output.
  • Use a server-side entitlement API when you need trustworthy enforcement.
  • If you add actual cryptographic authentication, define key provisioning, trust roots, rotation and verification outside an attacker-controlled client.

8. Review checklist for every new defense

  1. Write the exact tamper class the check is expected to detect.
  2. Specify the first instruction at which detection is guaranteed in the tested host.
  3. Add a clean non-attack test and a targeted mutation test.
  4. Test both handler mutation and independent reference mutation if relevant.
  5. Measure added cold-start/steady-state overhead.
  6. Test optional/missing debug APIs; distinguish unsupported API from attack.
  7. Document untested classes and host assumptions.
  8. Avoid silent fallback to a weaker mode on unverified output.

9. Scope of security claims

This project can make static inspection inconvenient, reject malformed payloads, and detect many selected runtime changes. It cannot establish confidential execution or complete anti-debug resistance when the attacker controls the interpreter. Describe security as coverage of explicitly tested alterations, not a universal numeric score.

3. Differential testing

Run original and protected code in equivalent environments with the same inputs. Compare:

  • returned values, including nil and return count;
  • emitted stdout/stderr (if relevant);
  • modifications to globals and external tables;
  • called host functions, with call order and argument values;
  • errors, exception timing and pcall results;
  • relevant metamethod invocations.

A simple single-return example:

local original = assert(loadfile('sample.lua'))
local protected = assert(loadfile('sample.obf.lua'))
assert(original() == protected())

That is not sufficient for arbitrary code. Programs may have side effects, multiple returns, nondeterminism, clocks and external I/O. The project verifier (src.verifier, exposed via Autofix.verify) provides a restricted sandbox comparison, but its result may be inconclusive. --strict-verify rejects an inconclusive build in the CLI.

5. Determinism and seed diversity

Same source, version, seed and options should produce the same artifact where the tool promises reproducibility. Different seeds should produce distinct mapping/layouts, but distinct bytes alone do not prove security. Snapshot output hashes for a fixed seed to catch accidental regressions; regenerate those baselines only after reviewing semantic changes.

lua v2/obfuscator.lua sample.lua a.lua --seed 123 --preset strong
lua v2/obfuscator.lua sample.lua b.lua --seed 123 --preset strong
# Compare a.lua and b.lua (sha256sum/cmp on POSIX).

6. Controlled mutation tests

Create one mutation at a time and hold all other conditions fixed.

Payload/VM mutation Expected behavior
Truncate bytecode body/header Explicit rejection before use
Alter declared plaintext length Length/checksum rejection
Change a fixed opcode ID to unknown Unknown opcode rejection
Set program counter to 0, fraction or too-large value CFI rejection
Replace one handler (and/or its backup) Expected reference check catches tested mutation
Add extra handler/prototype via rawset Shape/count check catches tested mutation
Tamper lazy-decoded prototype's total Prototype validation rejects
Alter a sealed chunk FNV or Adler Seal decoder rejects

Always run a clean control. A mutation test is successful when the defense behaves as specified, not when “some error happened.” Record the error category, detection point, runtime version and seed.

7. Property-based and fuzz testing

Generate bounded ASTs rather than unstructured random strings when testing semantics. Start with arithmetic and booleans, then tables/calls/closures. Set caps on expression depth, token count, runtime steps and memory; record a seed for replay. Classify failures into:

  1. parse failure (supported versus unsupported syntax);
  2. syntax-incorrect emitted Lua;
  3. output mismatch;
  4. timeout/hang;
  5. integrity rejection on clean input;
  6. targeted mutation not detected.

Shrink failing cases to the smallest AST and store as regression vectors. Never silently exclude a failure because it reproduces only for one seed.

8. Performance benchmark methodology

Measure five or more warm/cold repetitions of representative sources, on a fixed runtime/hardware with version information. Compare medians and the spread (range or p95), and record peak memory when the host exposes it. Do not combine source compile time with program execution time unless explicitly labeled.

Metric Definition Why it matters

Cold start launch process → first useful result loader/VM init cost
Steady state repetitive work after initialization dispatch overhead
File bytes compressed and expanded output sizes downloads/storage
Peak RSS OS-observed max resident memory low-memory targets
Runtime correctness output equivalence speed is irrelevant if wrong

Troubleshooting, Compatibility Matrix and Frequently Asked Questions

Use this document when a build fails, a VM file behaves differently, or the dashboard cannot compile. Prefer a minimal reproducible example, fixed seed and exact runtime version over a vague “sometimes broken” report.

1. First diagnostic steps

  1. Record the GsXFuscator version (lua v2/obfuscator.lua --version).
  2. Record Lua interpreter/version and operating system.
  3. Minimize the source while keeping the failure.
  4. Retry with --seed 12345 to stabilize randomized output.
  5. Save exact CLI flags and error stage.
  6. Run the original source in the target interpreter independently.
  7. Run the generated direct and sealed outputs separately to isolate the transport layer.
  8. Capture stdout, stderr, exit status, and any global side effects.

5. Frequently asked questions

Q: Can users make their own obfuscator from these docs?
Yes. The independent toy VM teaches the complete mechanism for a deliberately small grammar; the compiler, AST, ISA and extension guides explain how to expand it. Full Lua requires substantially more semantic and compatibility engineering.

Q: Is the packed payload encrypted with an unextractable secret?
No. Distributed code contains enough logic and material to run, and the host can inspect its runtime. Treat these methods as obfuscation/corruption detection, not secret-key custody.

Q: Does more decoy code always make protection stronger?
No. It can increase size and analysis noise, but a devirtualizer may ignore unused branches. Benchmark and run controlled analysis rather than scoring by function count.

Q: Can rawset be fully blocked with __newindex?
No. Lua metamethods can be bypassed with raw table operations. The runtime may detect some alterations using independent integrity checks, but the table itself is not absolutely immutable.

Q: Should I disable anti-debug if a host uses instrumentation?
First identify whether the host hook is legitimate and whether checks produce false positives. Document policy choices and test a clean/monitored pair. The browser's locked policy differs from CLI options.

Q: Why is --no-seal an option?
The sealed loader uses a dynamic load call that can be observed. Direct VM avoids that particular extra loader call but reveals VM source statically. It is a tradeoff, not universal protection.

Q: Does “verified” mean the script works on every platform?
No. The verifier compares behavior within its own sandbox and budgets; external APIs, concurrency and host differences need target-specific tests.

Q: Why are the parser and VM APIs labeled internal?
Their data structures are coupled to emission and may change as the compiler improves. The supported integration surface is Artifact.build, Obfuscate.run and the documented CLI/HTTP entry points.

Q: Can I bundle this into a site without a private build API?
The project includes a standalone browser build path. The private API is optional and has separate hosting, time and size constraints.

Q: What about the Discord address or output signature?
The V0.5 banner identifies GsXFuscator, links the same Discord invite and includes a Unicode ASCII comment. These are branding strings, not cryptographic signatures.

15Sealed transport specification⌄

V0.5 başlık uyumluluğu

V0.5 sealed dosya artık CLAX-V0.5|SEAL2 veya benzeri iç transport işaretiyle başlamaz. Tek dış başlık This, File Protected By GsXFuscator V0.5 markasıdır; hemen ardından kullanıcının Unicode ASCII sanatı yorum olarak, ardından loader kodu gelir. Bu durum blokların şifre çözme ve FNV/Adler doğrulama formatını değiştirmez. Seal.isWrapped yalnızca heuristik tespittir, kriptografik doğrulama değildir.

Seal V2 blok biçimi (V0.5 geçmişi, V0.5 başlığı güncellendi)

Kaynak: v2/src/seal.lua. Tarih: 2026-11-21. Bu belge güncel sürümü açıklar; önceki seal çıktılarının iç biçimi farklıdır.

Yol haritası

VM programı (Lua metni)
  -> 65536 baytlık ham bloklara ayırma (varsayılan)
  -> auto: LZSS dene, daha küçük değilse ham sakla
     raw: LZSS'i atla; lzss: sıkıştırılmış akışı zorla
  -> 12 baytlık blok başlığı ekle
  -> Kayan XOR byte stream dönüştürmesi
  -> 64 sembollü karıştırılmış base64 kodlama
  -> Tek Lua dosyası içinde blok tablosu (G)

Çalıştırma: base64 çöz -> XOR tersine çevir -> LZSS/ham -> iki hash kontrolü
          -> bütün blokları birleştir -> host load()/loadstring() -> VM çalıştır

Bu format LZ4 değildir; 2048 bayt pencereli özel bir LZSS varyantı kullanır.

Blok başlığı — 12 bayt

Ofset (0 bazlı) Boyut Anlamı
0–3 4 Little-endian ham uzunluk; 8388608 biti ham saklama bayrağı.
4–7 4 Önceki tüm çözülmüş bloklar üzerinden kümülatif FNV-1a32.
8–11 4 Önceki tüm çözülmüş bloklar üzerinden kümülatif Adler-32.
12… değişken Sıkıştırılmış bit akışı veya ham blok.

FNV-1a32 başlangıcı 2166136261, Adler-32 başlangıcı 1. Her blokta ikisi de güncellenir. Dış runtime nihai EXPECTED, EXPECTED_A değerlerini de kontrol eder. Bunların ikisi de sahteciliği kriptografik olarak engellemez: beklenen sabitler kod içinde bulunur.

LZSS

Tek bit: 0 ham byte, 1 geri referans. Geri referans 4 bit uzunluk eksi 3 ve 11 bit mesafe eksi 1 içerir; uzunluk aralığı 3–18, pencere 1–2048 bayttır. Akış MSB-first ilerler ve son byte dolgu bitlerinin sıfır olması gerekir. Geri referans hiçbir zaman henüz üretilmemiş bir baytı işaret edemez. Doğru ham uzunluğa ulaşıldığında decoder durur.

Kayan XOR

Her blokta durum 2166136261 + (blockIndex−1)×2654435761 (mod 2^32) biçiminde başlar. 16 baytlık K ile konuma bağlı katsayılar kullanılır. Bir önceki şifreli byte sonraki byte'a bağlanır. Bu bir stream-cipher taklididir; anahtar ve algoritma çıktı dosyasında olduğundan kriptografik şifreleme sayılmamalıdır.

Karıştırılmış base64

Alfabe 64 farklı yazdırılabilir sembolden üretilir; standart = dolgusu yerine 1 byte için 2, 2 byte için 3 sembol kullanılır. Çözücü geçersiz sembolleri ve sıfır olmayan terminal bitleri reddeder. Amaç basit dizgi taramalarının maliyetini artırmaktır, gizli anahtar saklamak değildir.

Decoder sınır kontrolleri

  • K 16, A 64 karakter olmalı ve alfabe tekrarsız olmalı.
  • M, T, D, N, EXPECTED ve EXPECTED_A alanları için tür, aralık ve tam sayı denetimleri bulunur.
  • Toplam 32 MiB üstü ham uzunluk reddedilir. Seal.wrap üst sınırı 32 MiB ile sınırlar; maxBytes yalnız bunu azaltabilir.
  • En az 12 bayt başlık ve bir payload baytı beklenir; blok sayısı toplam uzunlukla tutmalıdır.
  • Her blokta çözülmüş uzunluk tam eşleşmelidir; header/flag bozulması reddedilir.
  • FNV-1a ve Adler-32 her blokta ve sonunda eşleşmelidir.
  • Blok düzeyi hata invalid() yolundan standart hata döndürür.

Maliyet ve kapasite

  • Seal.BLOCK = 65536, Seal.MAX_BYTES = 33554432 (ham VM metni).
  • Base64 ve stream decode lineer maliyettedir. LZSS paketleyici, karma tablo araması içeren sınırlı backreference taraması yapar; büyük girdilerde zaman/alan maliyetini hedef host'ta ölçün.
  • Çıktı decoder'ındaki XOR artık 65.536 tam bayt kombinasyonlu tablo yerine 256 girişli nibble tablosuyla hesaplanır. Bu özellikle başlangıç belleği açısından iyileşmedir; her host'ta daha hızlı çalışacağı garanti değildir.
  • Birden fazla blok, geçici byte tabloları ve birleştirilmiş Lua metni yüzünden tepe bellek tüketimi tek dosya boyutunu geçebilir.

Sürümleme ve geriye dönük uyumluluk

Yeni üretilen dosyalar kendi decoder'larını taşır; bu nedenle eski dosyalar eski decoder ile çalışmaya devam edebilir. Buna rağmen blok formatı eski 8 baytlık başlıkla byte-uyumlu değildir. Eski G blob'larını yeni runtime'a elle yapıştırmayın; kodu yeniden üretin. Eski revizyonlar CLAX-V0.5|SEAL2 metaveri işareti taşıyabiliyordu. Bu V0.5 revizyonunun çıktısı bu işareti taşımaz. Eski işaretler dijital/kriptografik imza değildi.

Saldırgan modeli

Hata ve bozulma tespiti, bir istemciyi kontrol eden saldırgana karşı bütünlük ispatı değildir. Gerçek yetki kontrolü / lisans denetimi gerekiyorsa programın çalıştırıcısından bağımsız bir otorite veya sunucu kullanılmalıdır. Dış seal'in load() çağrısı incelenebiliyorsa --no-seal kullanmayı değerlendirin; bu seçim statik okunabilirlik takasını getirir.

Yeni sıkıştırma seçenekleri ve sınır hesabı

Seal.wrap(vm, seed, {compression="auto", blockSize=65536}) varsayılan davranıştır. compression="raw" LZSS aramasını atlar; zaten sıkışmayan payload'da üretimi hızlandırabilir. compression="lzss" LZSS'i zorlayarak sıkıştırılmış gövdenin ham gövdeden büyük olmasına da izin verir. Üç mod da aynı decoder'ı kullanır.

Zorunlu LZSS'te her literal byte 9 bit tutar. Dolayısıyla sıkıştırılmış boyut ham boyuttan büyük olabilir ve encoded-length kontrolü 12 + ceil(rawLen × 9/8) baytın base64 karşılığına kadar izin verir. Önceki rawLen+12 kontrolü, çok küçük bloklarda geçerli bir lzss paketini hatalı reddediyordu. Ham çıktı uzunluğu ve iki ayrı checksum ayrıca doğrulanır.

Paketleyicideki XOR lookup da 65.536 girdiden 256-entry nibble lookup'a indirilmiştir. Bu bellek tüketimini azaltır; hızlanma garantisi değildir.

V0.5 runtime dekoder performans notu

Format değişmedi. LZSS bit okuyucusu artık en fazla 11 bitlik alanları 24 bitlik, önceden sınır kontrolü yapılmış bir pencereden alır; p+bn > #t*8 reddi aynı sınır semantiğini korur. FNV-1a ve Adler-32 hash durumları birlikte ilerletilir, her blok sonunda ve tüm dosya sonunda her iki değer yine ayrı ayrı doğrulanır. Yanlış/veri dışı padding, yanlış uzunluk ve bozuk checksum hâlâ integrity check failed ile durur. Bu iki kontrol MAC veya imza değildir.
